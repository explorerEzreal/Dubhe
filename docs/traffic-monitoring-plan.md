# 流量监控分阶段实施规划

## 目标

建立从推理请求事实记录、Cloud 聚合、部署者分组/用户分析到调用者使用日志的完整流量观测体系。Token 统一记录输入、输出和总量，部署者可按分组查看具体调用用户，调用者只能查看自己的数据。

## 当前能力与缺口

- Cloud 已记录推理用户、API Key、设备、模型、状态和延迟。
- API Key 已绑定分组，Cloud 是唯一 PostgreSQL 访问者。
- 原有 `/api/usage` 仅返回调用次数、错误率和平均延迟。
- 需要保存请求发生时的分组快照，并补充 Token 聚合、用户维度、明细日志和时间趋势。

## 统计与权限口径

- Token 包括 `input_tokens`、`output_tokens`、`total_tokens`。
- 调用次数按 `inference_requests` 计数；失败、超时、取消和断线计入错误率。
- 部署者只能查看自己拥有的分组及分组内调用用户；调用者只能查看自己的请求和 API Key。
- 第一版支持今日、近 7 天、近 30 天和自定义时间，采用轮询刷新。

## 分阶段任务

### 阶段一：统计数据基础

增加请求 `group_id`、`total_tokens`、维度索引和历史回填策略，完善推理完成/失败/超时/取消/断线的持久化。

### 阶段二：Cloud 聚合接口

扩展 `/api/usage`，新增 `/api/monitoring`，提供总览、趋势、分组、用户、API Key、模型、设备和请求明细，并在 Cloud 层执行权限过滤。

### 阶段三：部署者看板

实现流量监控页，展示总览指标、Token 趋势、分组排行、分组内用户排行，并支持下钻到 API Key、模型、设备和请求；分组表与设备卡片增加 Token 摘要。

### 阶段四：调用者看板

增加个人 Token 汇总、API Key 排行、调用趋势、筛选和分页使用日志，支持 CSV 导出，不展示请求正文或响应正文。

### 阶段五：观察优化

增加 Token 突增、错误率突增、异常高频、无可用模型、数据新鲜度和缺失 Token 标记，后续再评估聚合表和告警通知。

## 验收要求

- 分组、用户、API Key、设备、模型汇总可相互校验。
- API Key 换组后历史请求仍归属原分组。
- 各角色不能越权查看数据。
- 迁移可重复执行，接口和页面连接真实数据。
- 每个阶段将变更、命令、结果和遗留风险记录到 `IMPLEMENTATION_PROGRESS.md`。
